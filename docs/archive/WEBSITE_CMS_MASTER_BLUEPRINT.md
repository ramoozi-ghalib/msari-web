تعتمد منصة مساري إستراتيجية الفصل القاطع بين الكيان التشغيلي والكيان التسويقي:

```
┌─────────────────────────────────────────┐        ┌─────────────────────────────────────────┐
│     Destination Core (الوجهة الأساسية)   │        │ Destination Details Page (تفاصيل الوجهة) │
├─────────────────────────────────────────┤        ├─────────────────────────────────────────┤
│ • تُدار وتُملك حصرياً بواسطة التطبيق       │        │ • تُدار وتُملك حصرياً بواسطة Website CMS  │
│ • تُجلب عبر API التطبيق (/v1/destinations)│        │ • تُخزن بـ Firestore (web_destination_pages) │
```

### 📋 جدول الفروقات الفنية والعلاقة الهيكلية:

## 🗄️ 3. تصميم مجموعات البيانات بـ Firestore (CMS Schema Blueprint)

تعتمد كافة المجموعات بادئة صريحة `web_` مع تحديد المالك والهدف والربط بـ API:

```
                               ┌───────────────────────────────────┐
                               │     Firebase Firestore Schema     │
                               └─────────────────┬─────────────────┘
                                                 │
          ┌──────────────────────────────────────┼──────────────────────────────────────┐
          ▼                                      ▼                                      ▼
  ┌───────────────┐                      ┌───────────────┐                      ┌───────────────┐
  │  web_settings │                      │   web_blocks  │                      │   web_pages   │
  └───────────────┘                      └───────────────┘                      └───────────────┘
          │                                      │                                      │
          ▼                                      ▼                                      ▼
  ┌───────────────┐                      ┌───────────────┐                      ┌───────────────┐
  │web_dest_pages │                      │    web_blog   │                      │   web_media   │
  └───────────────┘                      └───────────────┘                      └───────────────┘
```

### 📋 مواصفات المجموعات المعمارية:

1. **`web_settings`**:
   - **المالك**: Website Super Admin.
   - **الغرض**: إعدادات الموقع العامة (الهاتف، الواتساب، الشركاء، الـ SEO الافتراضي).
   - **علاقة API**: لا توجد.
   - **نوع البيانات**: Singleton Document (`web_settings/global`).

2. **`web_blocks`**:
   - **المالك**: Website CMS Editor.
   - **الغرض**: تخزين وتنسيق وترتيب البلوكات الديناميكية لـ Homepage Builder.
   - **علاقة API**: استعلام مدمج يقبل جلب الفنادق الممتازة من API التطبيق عند تفعيل `API_BLOCK`.
   - **نوع البيانات**: Collection documents (`block_hero`, `block_hotels`, etc.).

3. **`web_destination_pages`**:
   - **المالك**: Website CMS Content Team.
   - **الغرض**: المحتوى التحريري، المعالم، وكتالوج الصور لصفحة المدينة.
   - **علاقة API**: يرتبط بـ `cityId` القادم من API التطبيق.
   - **نوع البيانات**: Collection documents indexed by `slug`.

4. **`web_pages`**:
   - **المالك**: Website CMS Team.
   - **الغرض**: الصفحات التسويقية الثابتة (عن مساري، الخصوصية، الشروط، صفحة التطبيق).
   - **علاقة API**: لا توجد.
   - **نوع البيانات**: Collection documents indexed by `slug`.

5. **`web_blog` & `web_categories`**:
   - **المالك**: CMS Blog Writers & Editors.
   - **الغرض**: مقالات السفر والأدلة السياحية والتصنيفات.
   - **علاقة API**: لا توجد.
   - **نوع البيانات**: Articles collection with status index (`DRAFT`, `PUBLISHED`).

6. **`web_navigation` & `web_footer`**:
   - **المالك**: Website Admin.
   - **الغرض**: الهيكل الديناميكي للقوائم العلوية وقوائم الفوتر.
   - **علاقة API**: لا توجد.
   - **نوع البيانات**: Trees documents (`header_menu`, `footer_links`).

7. **`web_media`**:
   - **المالك**: CMS Media Manager.
   - **الغرض**: الفهرس الآمن ومكتبة الأصول وتتبع استخدامات الصور.
   - **علاقة API**: روابط الحاوية السحابية بـ Firebase Storage.

## 🖼️ 5. المعمارية التفصيلية لمكتبة الوسائط (Media Library Architecture)

تؤسس لوحة CMS لمركز إدارة أصول سحابي احترافي شامل:

```
                               ┌────────────────────────────────┐
                               │  Msari Media Manager Pipeline  │
                               └────────────────┬───────────────┘
                                                │
       ┌────────────────────────────────────────┼────────────────────────────────────────┐
       ▼                                        ▼                                        ▼
┌──────────────┐                       ┌─────────────────┐                      ┌─────────────────┐
│ File Policy  │                       │ Transform Engine│                      │ Storage & Audit │
├──────────────┤                       ├─────────────────┤                      ├─────────────────┤
│ Image, SVG,  │                       │ WebP Conversion │                      │ Storage: Firebase│
│ PDF, Lottie, │                       │ Responsive Res  │                      │ Audit: Safe Del │
│ Video, Docs  │                       │ Thumbnails Auto │                      │ Index: web_media│
└──────────────┘                       └─────────────────┘                      └─────────────────┘
```

### 5.1 الملفات المسموحة وحدود الحجم (MIME & Size Limits)
- **الصور (Images)**: `JPEG`, `PNG`, `WEBP` (الحد الأقصى: 5 MB).
- **الرسوم المتجهية (Vector/Icons)**: `SVG` مطهّرة (Sanitized SVG - الحد الأقصى: 1 MB).
- **الحركات (Animations)**: `JSON` (Lottie Files - الحد الأقصى: 2 MB).
- **المستندات (Documents)**: `PDF` (الحد الأقصى: 10 MB).
- **الفيديو (Video)**: `MP4`, `WEBM` (الحد الأقصى: 25 MB أو روابط خارجية من YouTube/Vimeo).

### 5.2 المعالجة الآلية والصور المتجاوبة (Image Processing Engine)
عند رفع أي صورة يتم تشغيل معالجة تلقائية:
1. **التحويل الآلي لـ WebP**: تحويل الصور تلقائياً لصيغة WebP عالية الضغط لتقليل الحجم بنسبة 70%.
2. **توليد النسخ المتجاوبة (Responsive Variants)**:
   - `thumbnail`: (150x150 px) لمعاينات لوحة التحكم.
   - `medium`: (600x400 px) لكروت الوجهات والمقالات.
   - `large`: (1920x1080 px) لخلفيات الهيرو والبنرات.

### 5.3 هيكلية التخزين وتسمية الملفات (Storage Hierarchy & Naming)
- **المسار**: `gs://msari-app-prod.appspot.com/website/{category}/{YYYY}/{MM}/{hash}-{slug}.webp`
- **التسمية القياسية**: تحويل اسم الملف لرمز آمن خالٍ من المساحات مع إضافة Timestamp وقيمة Hash فريدة.

### 5.4 الحذف الآمن وتتبع الاستخدام (Safe Delete & Reference Check)
- كل صورة تُسجل بـ `web_media` مع حقل `usedIn: Array<{ collection: string, docId: string }>`.
- عند محاولة حذف ملف، يتقرى المحرك حقل `usedIn`. إذا كانت الصورة مرتبطة ببلوك أو مقال، **يتم حظر الحذف فوراً** مع عرض رسالة تنبيه تحتوي قائمة الصفحات المرتبطة.

## 🧱 6. النظام المتقدم لباني الصفحة الرئيسية (Block-Based Homepage Engine)

تحول الصفحة الرئيسية إلى محرك ديناميكي قائم على الأنواع الأربعة للبلوكات:

```
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │  Homepage Block Engine                                                      │
 ├─────────────────────────────────────────────────────────────────────────────┤
 │ 1. Static Block    (نصوص ثابتة/عن المنظومة) ──► مخزنة بالكامل بـ Firestore   │
 │ 2. Dynamic Block   (سلايدر العروض والوجهات) ──► استعلام ديناميكي بـ Firestore│
 │ 3. API Block       (الفنادق الممتازة)       ──► جلب لحظي من API التطبيق      │
 │ 4. Reusable Block  (بنر تحميل التطبيق)        ──► بلوك مكرر بأكثر من صفحة   │
 └─────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 التحكم والنشر (Publishing & Version Control)
- **قواعد الظهور والجدولة (Visibility & Scheduling)**: تحديد تاريخ ووقت بدء وانتهاء ظهور البلوك (`startDate`, `endDate`).
- **المعاينة المسودة (Draft & Live Preview)**: إمكانية تعديل ترتيب ونصوص الأقسام ومعاينتها في نمط Draft على بيئة خاصة قبل النشر.
- **التراجع واستعادة النسخ (Rollback & Version History)**: الاحتفاظ بآخر 10 نسخ من تركيبة الصفحة الرئيسية وتوفير زر `Rollback` لاستعادة أي نسخة سابقة بنقرة واحدة.

## 🚀 7. التوسع المستقبلي (Future Extensibility Framework)

تم تصميم معمارية الـ CMS لتدعم التوسعات المستقبيلية دون الحاجة لإعادة هيكلة النظام:

1. **الصفحات الحملاتية والصفحات الهابطة (Landing Pages & Campaign Builder)**:
   دعم إنشاء صفحات هابطة مخصصة (`/landing/[campaign]`) باستخدام نفس محرك البلوكات Reusable Blocks.
2. **شبكات الفنادق والشركاء (Hotel Chains & Partner Portals)**:
   إمكانية إنشاء صفحات تعريفية مخصصة لسلاسل الفنادق والشركاء بداخل CMS.
3. **التدويل المتعدد (Multi-language Content)**:
   معمارية البيانات بـ Firestore مصممة بدعم الحقول المزدوجة (`Ar` / `En`) وجاهزة لإضافة أي لغة جديدة (`Fr`, `Ru`) بداخل الكائن المترجم دون تغيير الـ Schema.
4. **مساعد الذكاء الاصطناعي (AI Content Assistant Integration)**:
   توفير نقاط نفاذ جاهزة لربط محرر النصوص بـ Gemini API لتوليد صياغات المقالات، اقتراح عناوين الـ SEO، وترجمة المحتوى تلقائياً.
5. **شريط الإعلانات وقوالب الإشعارات (Announcement Bar & Templates)**:
   دعم إدارة الشريط العلوي للتنبيهات بمشروع الـ Web وقوالب البريد الإلكتروني.

## 🔐 9. التوصيف التشغيلي للأدوار والصلاحيات (Expanded Roles & Operations)

1. **Super Admin (مدير النظام الأقصى)**:
   - ملكية كاملة وغير مقيدة لكافة الأقسام والإعدادات.
   - إضافة وحذف المشرفين، تعديل أدوارهم، وإدارة الـ Roles.
   - النشر المباشر وتجاوز مراجعات المحتوى.

2. **Administrator (مدير CMS)**:
   - إدارة كافة الأقسام التحريرية والتسويقية و SEO.
   - لا يملك صلاحية تعديل حسابات Super Admins أو الإعدادات الحساسة للنظام.

3. **SEO Manager (مدير محركات البحث)**:
   - الوصول المباشر لكافة حقول الـ Meta Tags, Canonical URLs, Structured Data, Robots.txt.
   - إمكانية تعديل وعرض الـ SEO لكافة الصفحات دون تعديل محتوى النصوص الأصلي.

4. **Editor (المحرر)**:
   - مراجعة المقالات والصفحات المرسلة من الكُتّاب (`Draft` ➔ `Review`).
   - اعتماد النشر أو إرجاع المحتوى للملاحظات.
   - إدارة مكتبة الوسائط بدون صلاحية حذف الملفات المستخدمة.

5. **Writer (الكاتب)**:
   - إنشاء مقالات مسودة جديدة بـ `web_blog`.
   - رفع الصور الخاصة بمقالاته فقط.
   - إرسال المقال للمراجعة (`Submit for Review`) دون صلاحية النشر المباشر.

6. **Content Reviewer (مراجع المحتوى)**:
   - صلاحية قراءة ومعاينة مسودات الصفحات والمقالات وتدوين الملاحظات دون صلاحية التعديل المباشر.

## 📜 10. سجل القرارات المعمارية المعتمد (Architectural Decision Records - ADR)

### 📄 ADR-001: اعتماد Firebase Firestore بالكامل
- **القرار**: استخدام Firebase Firestore كمصدر بيانات واحد وحصري لـ Website CMS.
- **السبب**: التكامل الأصيل مع تطبيق الجوال (الذي يستخدم Firebase بالفعل)، تقليل التكاليف التشغيلية، ومشاركة جلسات الأمان والـ Security Rules.

### 📄 ADR-002: رفض استخدام Supabase PostgreSQL
- **القرار**: استبعاد Supabase وحذف عميلها من المشروع بإنهاء رفع الصور بـ Firebase Storage.
- **السبب**: منع ازدواجية قواعد البيانات (Dual-DB Architecture)، وتجنب تعقيدات مزامنة البيانات وتأخيرات الـ Connection Pooling ببيئات الـ Serverless.

### 📄 ADR-003: الإبقاء على مسار اللوحة بداخل `msari.com/admin`
- **القرار**: عدم فصل اللوحة بـ Subdomain مستقل (`cms.msari.com`) والإبقاء عليها بـ `/admin`.
- **السبب**: ضمان التدويل المباشر بـ Next.js App Router (`/ar/admin`), وسهولة قراءة الـ Auth Session Cookies الموحدة.

### 📄 ADR-004: عدم تكرار أو نسخ بيانات التطبيق داخل Firestore CMS
- **القرار**: حظر نسخ بيانات الفنادق، الغرف، والحجوزات بداخل مجموعات الـ CMS.
- **السبب**: منع تضارب البيانات (Data Drift) والالتزام بحظر ازدواجية البيانات، مع الاعتماد الحصري على API التطبيق للبيانات التشغيلية.

### 📄 ADR-005: اعتماد باني الصفحة الرئيسية القائم على البلوكات (Block-Based Homepage)
- **القرار**: تحويل الصفحة الرئيسية إلى كائن ديناميكي مرن (`web_blocks`).
- **السبب**: تمكين فريق التسويق من إعادة ترتيب وإخفاء وتعديل عناصر الصفحة الرئيسية دون التعديل على الكود المصدر.
